Security

One GearOut installation serves one institution. There is no shared database, no shared process, and no cross-customer data path.

The stack

Six containers on one host: Apache for TLS termination and reverse proxy (the only container with published ports), the web application, a background worker, PostgreSQL 17 with row-level security enabled, Redis for the job queue, and MinIO for uploaded images. Every container except Apache sits on a private network.

Identity and access

  • Sign-in methods, configured per installation from the admin page: Microsoft Entra ID (OIDC), Google Workspace (OIDC, with an optional hosted-domain restriction), and SAML 2.0 through the SSOReady broker, which covers Shibboleth, ADFS, and Okta.
  • LMS launch: LTI 1.3 with OIDC login, single-use state, and JWKS verification of the platform token. Roster membership arrives through LTI Names and Role Provisioning Services.
  • Roles: student, instructor, admin, superadmin. Desk operations are open to instructor and above; inventory, users, fines, and settings require admin; authentication providers and API tokens require superadmin. Every API route declares its access level in one wrapper, so a route cannot be added without a gate.
  • API tokens for scripts and integrations: only the SHA-256 hash is stored, comparison is constant-time, roles are read, desk, and admin, and a read-only token is refused on any mutating call. Creation and revocation are audited.
  • Sign-in attempts are rate limited to 20 per source address per minute.
  • PostgreSQL row-level security policies on every tenant table. The application runs as a restricted database role that cannot bypass them.

Data protection

  • In transit: TLS at Apache with a Let's Encrypt certificate or one the institution provides, plus Strict-Transport-Security, Content-Security-Policy, and the related headers.
  • At rest: integration secrets (LMS tokens, OIDC client secrets, SAML broker secrets) are encrypted with AES-256-GCM under a key held in the environment and never stored in the database. Disk encryption for the database volume is the host's.
  • No payment card data exists in the system.
  • Uploads accept PNG, JPEG, and WebP only, validated server-side; SVG is refused.
  • The browser service worker caches the application shell and the student's last pickup pass for offline display. It never caches API responses.
  • Audit records store a coarsened client address, and audit rows are pruned after 90 days by a scheduled job.

What data leaves the stack

Inbound only: LTI claims from the LMS and sign-in claims from the identity provider. Outbound only: transactional email to the student's own address (confirmation, reminder, overdue, renewal decision, waitlist offer). Nothing goes to SIM DAD. For managed delivery, SIM DAD operates your stack, one stack for you alone.

What is not claimed

No SOC 2, ISO 27001, or other third-party attestation. No penetration test has been commissioned yet Roadmap. No native mobile app. No AI or machine-learning feature processes student data; the API and command-line tooling exist for administrators' own automation.
